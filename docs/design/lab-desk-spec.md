# Lab Desk 동작 명세 — 장치 식별 · rig · 화면 · 테스트

- Issue: #2 (umbrella #1)
- Status: 명세 확정, 구현 전
- 선행 문서: [`jetson-lab-desk.md`](jetson-lab-desk.md) — 탐색·배포·터널
- 기준 실측: 2026-08-18, JetsonOrinNanoSuper + 카메라 3대

## 0. 이 문서의 범위

선행 문서가 "Jetson에 어떻게 닿고 어떻게 설치하는가"를 다룬다면, 이 문서는
**닿은 다음 무엇을 하는가**를 다룬다. 장치를 어떻게 식별하는지, 하드웨어 구성을
어떻게 등록하고 대조하는지, 화면에 무엇이 있고 테스트가 무엇을 받는지.

한 문장으로 줄이면 이 명세의 목적은 하나다.

> **카메라 2대가 보이는 것은 사실일 뿐이다. "3대여야 하는데 2대"가 되어야 오류다.**

앱이 오류를 오류라고 부르려면 기대 구성을 알아야 한다. 그 기대 구성이 `rig`이다.

## 1. 실측 기준

이 명세의 모든 판단은 아래 실측에서 나왔다. 추정이 아니라 확인된 값이다.

### 1.1 카메라에 고유 ID가 없다

3대 전부 같은 값을 보고한다.

| 항목 | 값 |
| --- | --- |
| VID:PID | `1bcf:2d50` (3대 동일) |
| `serial` | `01.00.000` (3대 동일) |
| `bcdDevice` | `0234` (3대 동일) |

`serial`은 개체 번호가 아니라 펌웨어 버전 문자열이다. **MAC에 해당하는 값이 없다.**
따라서 "카메라마다 고유 ID를 읽어 alias를 붙인다"는 방식은 이 하드웨어에서
성립하지 않는다.

### 1.2 `/dev/v4l/by-id/`는 깨져 있다 — 쓰면 안 된다

노드는 6개인데 심링크는 4개뿐이다. 이름이 겹쳐 udev가 덮어썼다.

```
usb-DCXIN_DCXIN_Camera_01.00.000-video-index0 -> ../../video2   ← 포트 1.2 카메라
usb-DCXIN_DCXIN_Camera_01.00.000-video-index1 -> ../../video1   ← 포트 1.1 카메라
```

한 이름 밑에 서로 다른 카메라의 노드가 섞여 있다. **없는 것보다 나쁘다** — 그럴듯한
이름이라 믿고 쓰게 된다. by-id는 이 명세에서 금지한다.

### 1.3 안정된 키는 USB 포트 경로 하나뿐

`/dev/v4l/by-path/`는 6개 전부 정확하다.

| 허브 포트 | `ID_PATH` | 캡처 노드 | 메타데이터 노드 |
| --- | --- | --- | --- |
| 1 | `platform-3610000.usb-usb-0:1.1:1.0` | `/dev/video0` | `/dev/video1` |
| 2 | `platform-3610000.usb-usb-0:1.2:1.0` | `/dev/video2` | `/dev/video3` |
| 3 | — | (비어 있음) | — |
| 4 | `platform-3610000.usb-usb-0:1.4:1.0` | `/dev/video4` | `/dev/video5` |

토폴로지: Jetson USB 3.0 root → Realtek 4포트 허브(`0bda:0489`) → 포트 1·2·4.
케이블을 옮기지 않는 한 재부팅해도 이 경로는 유지된다.

### 1.4 노드 수는 카메라 수의 2배다

카메라 1대가 노드 2개를 만든다. 짝수 노드만 캡처되고 홀수 노드는 메타데이터라
열리지 않는다(직접 열어 확인: `video0/2/4`만 `read=True`).

지금 `uvc_devices.list_devices(max_index=5)`가 3대를 맞게 찾는 것은 **우연이다.**
카메라가 4대가 되면 노드가 8개가 되어 `max_index=5`로는 마지막 카메라를 못 찾는다.
**index 스캔을 by-path 열거로 바꾼다** (§2.2).

### 1.5 3대가 같은 물건이 아니다 — 가장 중요한 발견

V4L2 컨트롤 범위를 조회한 결과, 포트 4번 카메라만 컨트롤 맵이 다르다.

| 컨트롤 | 포트 1·2 (DCXIN) | 포트 4 (DECXN) |
| --- | --- | --- |
| Backlight Compensation | min 0 / max **3** / default 0 | min 16 / max **160** / default 72 |
| Hue | min 1 / max 200 / default 200 | min −128 / max 128 / default 0 |
| Exposure Time, Absolute | 1–10000 / default 156 | 1–10000 / default 156 |
| Auto Exposure | 0–3 / default 3 | 0–3 / default 3 |

rack-tracker `docs/etc/camera-sync/fsin-trigger-wiring.md`가 정리한 대로, 이 모듈의
**트리거 모드 스위치는 Backlight Compensation**이다 (0=자유구동, 1=소프트 트리거,
2=하드웨어 트리거, 3=명령 단프레임). 포트 1·2는 범위가 정확히 `0..3`으로 이 표와
일치한다. 포트 4는 `16..160`짜리 **평범한 웹캠 컨트롤**이다.

즉 **포트 4번 카메라에는 트리거 펌웨어가 없다.** FSIN 하드웨어 트리거를 3대에 동시
인가하는 계획은 지금 꽂혀 있는 이 조합으로는 성립하지 않는다. 제조사 문자열도
`DECXN`/`DECXIN Camera`로 나머지 둘(`DCXIN`/`DCXIN Camera`)과 다르고, YUYV
1920×1200에서 드라이버가 보고하는 fps도 60(나머지는 30)이라 다른 물건이라는 신호가
여러 개 겹친다.

**이 발견이 이 명세 전체의 존재 이유다.** 손으로 SSH 붙어 테스트했다면 3대가 다 잡히고
프레임도 다 나오니 정상으로 보였을 것이고, 트리거를 걸었을 때 한 대만 안 따라오는
현상을 배선 문제로 오해했을 것이다. 구성을 선언해두고 대조했다면 **테스트를 돌리기
전에** 잡혔다.

### 1.6 OS는 JetPack 6

| 항목 | 값 |
| --- | --- |
| OS | Ubuntu 22.04.5 LTS |
| L4T | R36 (release), REVISION 5.0 |
| 아키텍처 | `aarch64` |
| Python | 3.10.12 (시스템) |
| OpenCV | 4.8.0 (시스템에 이미 있음) |
| `uv` | 없음 |
| `v4l2-ctl` | 없음 |

선행 문서가 대비한 "JetPack 5의 python3.8이 `requires-python >=3.10`에 미달" 문제는
**이 장비에는 없다.** bootstrap의 `uv python install` 단계는 다른 Jetson을 위해
남기되, 이 장비에서는 건너뛰는 것이 정상 경로다.

`v4l2-ctl`이 없다는 것은 곧 **트리거 모드 전환을 OpenCV로 해야 한다**는 뜻이다:
`cap.set(cv2.CAP_PROP_BACKLIGHT, 2)`, 주파수는 `cv2.CAP_PROP_HUE`.

## 2. 장치 식별 — 포트가 신원이다

### 2.1 `camId`

```
camId = ID_PATH에서 뽑은 포트 경로     예) "usb-0:1.1"
```

`ID_PATH`의 `platform-3610000.usb-` 접두어는 Jetson의 USB 컨트롤러를 가리키므로
`rig.host.usbRoot`에 한 번만 저장하고, `camId`에는 포트 부분만 남긴다.

**hash를 씌우지 않는다.** 포트 경로는 이미 짧고, 고유하고, 사람이 읽을 수 있다.
hash로 감싸면 사람이 못 읽게 되어 스티커·로그·오류 메시지에서 전부 손해다.

스티커용 짧은 코드가 필요하면 허브 포트 번호를 그대로 쓴다 — `P1`, `P2`, `P4`.

### 2.2 열거 방법

`/dev/video*` index 스캔을 **하지 않는다.** `/sys/class/video4linux/*` 를 훑어
각 노드의 `ID_PATH`와 `index` 속성을 읽고, `index=0`인 노드만 캡처 노드로 채택한다.
같은 `ID_PATH`를 가진 노드들은 한 카메라다.

이 방식은 카메라 수에 상한이 없고, 메타데이터 노드를 카메라로 오인하지 않으며,
열어보지 않고도 목록을 만들 수 있다(다른 프로세스가 쓰는 중이어도 목록에는 나온다).

**노드 번호는 실제로 돌아간다.** 2026-08-19 실물 검증에서 카메라 한 대가 USB
결함으로 사라졌다가 다른 포트로 돌아왔고, 그 결과 `P1`은 `/dev/video0`에서
`/dev/video4`가 됐다 — 같은 하루 안에, 같은 장비에서. 인덱스로 카메라를 지목했다면
그 시점부터 다른 카메라를 측정하고 있었을 것이다. 포트를 신원으로 쓰는 이유가
가정이 아니라 관측이라는 뜻이다.

**프로브에는 시간 제한이 있다.** 크기·시그니처를 채우려면 한 번은 열어야 하는데,
USB 링크가 무너지는 카메라는 노드를 남긴 채 open/read에서 무한정 멈춘다. 실물에서
이것 하나가 열거를 붙잡아 서버 전체를 잠갔다. 프로브는 별도 스레드에서 8초까지만
기다리고, 못 지킨 장치는 `opened=false` + `probeError="timeout"`으로 보고한다.

### 2.3 앱이 감지할 수 있는 것과 없는 것

| 상황 | 감지 |
| --- | --- |
| 대수가 줄었다 / 늘었다 | O |
| 빈 포트(P3)에 새로 꽂혔다 | O |
| 등록된 포트에 성격이 다른 카메라가 꽂혔다 (§2.4) | O |
| 허브가 통째로 다른 Jetson 포트로 옮겨졌다 | O — 경로 접두어가 한꺼번에 바뀐다 |
| 보이는데 열리지 않는다 (다른 프로세스 점유) | O — `probeError="busy"` |
| 보이는데 응답하지 않는다 (USB 결함) | O — `probeError="timeout"`, 화면에는 "응답 없음" |
| **같은 모델 2대를 서로 바꿔 꽂았다** | **X — 영원히 모른다** |

마지막 줄은 §1.1의 직접적인 결과다. 소프트웨어로 막을 방법이 없다.

### 2.4 컨트롤 프로파일 — 약한 신원

개체 식별은 못 해도 **성격 식별**은 된다. §1.5의 컨트롤 범위를 지문으로 쓴다.

| 프로파일 | 판별 조건 | 의미 |
| --- | --- | --- |
| `trigger-v1` | Backlight `0..3` **그리고** Hue `1..200` | 트리거 모드 스위치 있음 |
| `webcam-std` | Backlight `16..160` | 일반 웹캠, 트리거 불가 |
| `unknown` | 위 어느 쪽도 아님 | 처음 보는 물건 |

rig에 포트별로 기대 프로파일을 저장해두면, 카메라를 다른 종류로 바꿔 꽂았을 때
잡힌다. 그리고 §8의 `requires`가 이 값을 보고 **불가능한 테스트를 실행 전에 거부**한다.

### 2.5 물리 마킹 규약

앱은 포트만 본다. 사람은 §2.3의 마지막 줄을 담당한다.

- 허브의 각 포트에 `P1` `P2` `P4` 표시
- 각 카메라 몸체와 케이블 끝에 같은 표시
- 규약: **같은 표시끼리만 꽂는다**

마킹은 앱의 대체재가 아니라 앱이 못 하는 부분의 담당이다. 이 점을 등록 화면에
한 줄로 적어 사용자가 오해하지 않게 한다.

### 2.6 허브 이동

모든 `camId`가 같은 규칙으로 한꺼번에 바뀌면(예: `usb-0:1.*` → `usb-0:2.*`) 이는
카메라가 아니라 허브가 옮겨진 것이다. 이 경우 앱은 실패로 처리하지 않고 다음을
제안한다.

> 허브가 다른 포트로 옮겨진 것 같습니다. 매핑을 통째로 옮길까요? (`1.x` → `2.x`)

수락하면 `camId`만 일괄 치환하고 라벨은 유지한다. 카메라 대수와 각 포트의
컨트롤 프로파일이 전부 일치할 때만 제안한다.

## 3. rig — 데이터 모델

### 3.1 저장 위치

**Jetson의 `~/.uvc-lab/rig.json`.**

배선은 Jetson에 붙어 있는 물리적 사실이지 노트북의 사정이 아니다. 노트북을 바꾸거나
다른 사람이 다른 노트북으로 붙어도 같은 기준이 따라온다. 노트북에 두면 랙은 그대로인데
기준만 사라진다. (SSH 비밀번호는 반대다 — 그건 노트북에 둔다.)

### 3.2 스키마

```jsonc
{
  "rigVersion": 1,
  "name": "레일 3카메라",
  "createdAt": "2026-08-18T14:02:11+09:00",
  "host": {
    "hostname": "JetsonOrinNanoSuper",
    "usbRoot": "platform-3610000.usb"
  },
  "cameras": [
    {
      "camId": "usb-0:1.1",
      "label": "좌",
      "mark": "P1",
      "expect": {
        "vidPid": "1bcf:2d50",
        "manufacturer": "DCXIN",
        "product": "DCXIN Camera",
        "bcdDevice": "0234",
        "controlProfile": "trigger-v1"
      },
      "connector": "jst-3p-strb-trg-gnd",
      "wiring": { "TRG": true, "STRB": false, "GND": true }
    },
    { "camId": "usb-0:1.2", "label": "중", "mark": "P2", "expect": { "...": "..." },
      "connector": "jst-3p-strb-trg-gnd", "wiring": { "TRG": true, "STRB": false, "GND": true } },
    {
      "camId": "usb-0:1.4",
      "label": "우",
      "mark": "P4",
      "expect": {
        "vidPid": "1bcf:2d50",
        "manufacturer": "DECXN",
        "product": "DECXIN Camera",
        "bcdDevice": "0234",
        "controlProfile": "webcam-std"
      },
      "connector": "jst-3p-strb-trg-gnd",
      "wiring": { "TRG": false, "STRB": false, "GND": false }
    }
  ],
  "trigger": {
    "source": { "gpioBoardPin": 7, "name": "GPIO09" },
    "strobeReturn": { "gpioBoardPin": 11, "name": "GPIO17" },
    "levelShift": "3.3V->1.8V (BSS138)",
    "verifiedAt": null
  }
}
```

`wiring`은 **선언값이다.** 앱은 배선을 볼 수 없다. 전부 `false`가 기본이고, 사용자가
다이어그램에서 체크해야 `true`가 된다. 맞는지는 §7.4의 검증 동작이 판정한다.

"트리거 대상 카메라 목록"을 따로 두지 않는다. `wiring.TRG === true`인 카메라가 곧
대상이므로, 같은 사실을 두 군데 적어 어긋나게 만들 이유가 없다.

`trigger.source`가 없으면(= GPIO 핀 미지정) 어떤 카메라도 `TRG`를 체크할 수 없다.
펄스를 낼 곳이 없는 배선은 선언 자체가 성립하지 않는다.

## 4. rig 등록 흐름

폼을 채우게 하지 않는다. **탐지 결과에 라벨만 얹는다.**

1. 앱이 §2.2 방식으로 현재 장치를 전부 열거하고 §2.4 프로파일을 판정한다
2. 각 카메라의 프리뷰를 동시에 띄운다
3. 사용자가 손으로 렌즈를 가려 어느 칸이 어느 카메라인지 확인하고 라벨을 입력한다
   (`좌` `중` `우`처럼 자유 문자열)
4. 트리거 배선을 등록한다 — 안 했으면 건너뛴다
5. **"이 구성을 기준으로 저장"** → `rig.json` 생성

사용자가 실제로 하는 입력은 라벨 n개와 GPIO 핀 번호 하나뿐이다.

프리뷰를 3대 동시에 띄우는 것 자체가 §1.5 같은 문제를 드러내는 첫 관문이므로,
등록 화면은 대역폭을 아끼지 말고 전부 띄운다.

## 5. 대조 규칙 — 상태 7종

연결할 때마다, 그리고 사용자가 새로고침할 때마다 rig과 현재 상태를 대조한다.

| 상태 | 조건 | 화면 동작 |
| --- | --- | --- |
| `ok` | 등록된 모든 `camId`가 존재하고 프로파일 일치 | 랩 화면 진입 가능 |
| `missing` | 등록된 `camId`가 안 보임 | 라벨로 지목: "좌측 카메라(P1)가 안 보입니다" |
| `unknown-device` | 등록 안 된 포트에 장치 있음 | "P3에 등록되지 않은 카메라가 있습니다" + rig에 추가 제안 |
| `changed-device` | 포트는 맞는데 VID:PID 또는 프로파일 불일치 | "P4에 다른 카메라가 꽂혀 있습니다" |
| `busy` | 목록에는 있는데 열리지 않음 | "P2를 다른 프로세스가 쓰고 있습니다" — 일반 오류로 뭉뚱그리지 않는다 |
| `hub-moved` | 전체가 같은 규칙으로 이동 | §2.6 제안 |
| `no-rig` | `rig.json` 없음 | 등록 화면으로 |

`ok`가 아니면 랩 화면 진입을 막는다. 다만 **"무시하고 진행"을 남긴다** — 카메라 1대만
빼고 테스트하고 싶은 정당한 경우가 있다. 이때는 실행 결과에 `rigStatus`를 같이 기록해서
나중에 그 숫자가 어떤 구성에서 나온 것인지 남는다.

## 6. 배선 다이어그램

### 6.1 무엇을 그리는가 — 노드는 Jetson과 카메라뿐

허브·레벨 시프터·브레드보드는 노드로 그리지 않는다. 그려봐야 화면만 복잡해지고,
사용자가 할 일(실제 배선)이 줄지 않는다.

다만 **포트 번호는 카메라 노드에 남긴다.** §2.1대로 포트가 곧 카메라의 신원이라,
지우면 어느 카메라 이야기인지 말할 수 없게 된다. 허브는 노드가 아니라 줄기 선 위의
글자로만 표시한다.

drag & drop은 만들지 않는다. 배치는 고정 레이아웃이고, 사용자가 조작하는 것은
카메라 추가/제거와 체크박스뿐이다.

### 6.2 Jetson 노드 — 기본으로 놓여 있다

장비가 Jetson 한 종류뿐이므로 고를 것이 없다. 접속된 Jetson이 자동으로 놓이고
지울 수 없다. 이 노드가 갖는 편집 항목은 GPIO 핀 배정 둘이다.

| 항목 | 기본값 | 비고 |
| --- | --- | --- |
| 트리거 출력 | BOARD 핀 7 (GPIO09) | `TRG`를 하나라도 체크하려면 필수 |
| STROBE 입력 | BOARD 핀 11 (GPIO17) | 선택. 안 쓰면 비워둔다 |

기본값은 rack-tracker `docs/etc/camera-sync/fsin-trigger-wiring.md` §2 핀맵에서
가져왔다. 핀 번호는 `Jetson.GPIO`의 **BOARD** 번호이고, 다른 핀을 써도 되므로
편집 가능하게 둔다.

### 6.3 카메라 노드 — 추가 / 제거

- **탐지된 것 불러오기** — §2.2 열거 결과를 한 번에 놓는다. 보통은 이걸로 끝난다.
- **카메라 추가** — 아직 안 꽂힌 카메라를 미리 놓는다. 배선을 먼저 계획할 때 쓴다.
  포트가 정해지지 않았으므로 `camId`가 비어 있는 **미바인딩** 상태다.
- **선택 제거** — rig에서 뺀다. 실제로 꽂혀 있는 카메라를 지우면 §5의
  `unknown-device`로 다시 올라온다. 앱이 임의로 되살리지는 않는다.

미바인딩 카메라는 장치가 나타났을 때 바인딩한다. 후보 포트가 하나뿐이면 자동으로,
여럿이면 사용자가 고른다. §1.1 때문에 앱에는 "이 카메라가 그 카메라"라고 판단할
근거가 없으므로, 애매하면 반드시 사람에게 묻는다.

### 6.4 신호 체크박스

카메라 노드마다 커넥터 프로파일이 있고, 프로파일이 신호 목록을 준다.

`jst-3p-strb-trg-gnd` (지금 장비):

| 신호 | 방향 | 전압 도메인 | 체크 |
| --- | --- | --- | --- |
| `STRB` | 카메라 → Jetson (노출 구간 출력, active-high) | 1.8V | 선택 |
| `TRG` | Jetson → 카메라 (트리거 입력, = FSIN) | 1.8V | 선택 |
| `GND` | 신호 GND | — | **자동** |

출처는 같은 문서 G-3 항목이다 — 보드 실크에 `STRB` / `TRG` / `GND` 순으로 인쇄돼
있고, 벤더 사용설명서 §9의 핀 정의(3=Trigger, 4=Strobe/Flash, 5=GND)와 일치한다.
센서 데이터시트의 `FSIN`은 실크의 `TRG`와 같은 핀이다.

규칙 셋:

- **`GND`는 사용자가 못 끈다.** `STRB`나 `TRG` 중 하나라도 체크하면 자동으로 켜지고,
  둘 다 끄면 자동으로 꺼진다. GND 없는 신호선은 배선이 아니라 오배선이므로 선택지로
  두지 않는다.
- **`TRG`는 `controlProfile: "trigger-v1"`에서만 체크할 수 있다.** §1.5에서 확인한
  대로 P4 카메라에는 트리거 펌웨어가 없다. 배선을 해도 모드 진입이 안 되므로
  체크박스를 비활성화하고 이유를 옆에 적는다 — 배선 다 하고 나서 알게 되면 늦다.
- **`STRB`는 컨트롤 프로파일과 무관하다.** 노출 구간 출력은 펌웨어 모드와 별개로
  살아 있다(rack-tracker 실측 1.627V, 조명에 따라 변동). 계측용이므로 어느
  카메라에서든 체크할 수 있다.

커넥터에 핀이 더 있는 모델이 들어오면 프로파일에 신호를 추가한다. 화면은 목록을
그대로 그리므로 화면 코드는 고치지 않는다.

### 6.5 전압 경고

`TRG`·`STRB` 둘 다 **1.8V 도메인**이다. 3.3V를 직접 넣으면 핀이 파손된다
(rack-tracker G-2 항목, 벤더 문서 §9). 앱은 레벨 변환이 되어 있는지 확인할 방법이
없으므로, `TRG`나 `STRB`를 처음 체크하는 순간 이 경고를 한 번 띄운다. 막지는
않는다 — 실제 배선은 사용자 몫이고, 앱이 할 수 있는 일은 모르고 지나가지 않게
하는 것까지다.

### 6.6 렌더링 규칙

```
  JetsonOrinNanoSuper                    trigger  BOARD 7  (GPIO09)
       │                                 strobe   BOARD 11 (GPIO17)
       │  USB 3.0 — Realtek 4-port hub
       ├──── P1 ● 좌  DCXIN  video0  trigger-v1   [x] TRG  [ ] STRB  [x] GND
       │        ┆ TRG (선언, 미검증)
       ├──── P2 ● 중  DCXIN  video2  trigger-v1   [x] TRG  [ ] STRB  [x] GND
       │        ┆ TRG (선언, 미검증)
       ├──── P3 ○ (비어 있음)
       └──── P4 ● 우  DECXN  video4  webcam-std   [-] TRG  [ ] STRB  [ ] GND
                                                   └ 트리거 펌웨어 없음
```

- **실선 = 관측.** 앱이 실제로 읽은 것만 실선으로 그린다. USB 연결이 여기 해당한다.
- **점선 = 선언.** 체크박스로 켠 신호선은 점선이다. §7.4 검증을 통과하면 실선으로
  바꾸고 `trigger.verifiedAt`을 기록한다. 주장과 관측이 화면에서 구분되어야 한다.
- **미바인딩 카메라는 노드 테두리도 점선**으로 그린다. 같은 규칙의 연장이다.
- 빈 포트도 그린다(`○`). 어디에 꽂을 자리가 남았는지가 배선 작업에 필요한 정보다.
- rig의 기대와 다른 포트는 색으로 표시한다(§5).

각 카메라 노드에는 신호 체크박스 외에 테스트용 토글도 붙는다 — §8의 테스트 프로필을
이 다이어그램 위에서 직접 만든다.

| 토글 | 값 |
| --- | --- |
| 이 테스트에 포함 | on / off |
| 트리거 모드 | 자유구동 / 소프트 / 하드웨어 (`trigger-v1` + `TRG` 체크일 때만 활성) |
| 해상도·포맷 | MJPG 1920×1200 등 |

## 7. 랩 화면 — 동작 목록

### 7.1 프리뷰

카메라별 MJPEG 스트림. 여러 대 동시 표시. Tailscale 경로에서는 느리다는 것을
선행 문서가 이미 기록해뒀다.

**프레임이 오지 않으면 그렇게 적는다.** 열리기는 하는데 프레임을 내보내지 않는
카메라가 실제로 있었다(§12). `<img>`는 그 상태에서 오류도 내지 않고 영원히 비어
있으므로, 타일이 스스로 알아채야 한다 — MJPEG은 `onLoad`를 쏘지 않지만 첫 프레임이
디코드되면 요소에 크기가 생긴다. 6초까지 크기가 없으면 "프레임 없음 — 카메라가
응답하지 않습니다"를 붙이고, 늦게라도 프레임이 도착하면 그 표시를 지운다(느린
카메라를 죽었다고 단정하지 않기 위해서다).

### 7.2 모드 전환

해상도·포맷·요청 fps. `set` 후 실제로 무엇이 잡혔는지 되읽어서 **요청값이 아니라
관측값을 표시한다.** 드라이버가 조용히 다른 값을 주는 일이 흔하다.

### 7.3 파라미터

노출(수동/자동), 게인 등. 컨트롤별 min/max/step/default를 §1.5처럼 장치에서 직접
조회해서 UI 범위로 쓴다. 하드코딩하지 않는다 — 같은 모델이라도 범위가 다르다는 것이
이미 확인됐다.

### 7.4 트리거 검증

`wiring.TRG`가 `true`인 카메라에서만 나온다. 앱이 배선을 볼 수 없으므로 **간접 검증**한다.

1. 대상 카메라를 `CAP_PROP_BACKLIGHT = 2`(하드웨어 트리거)로 전환
2. 펄스를 주지 않은 상태에서 프레임이 멈추는지 확인 — 계속 나오면 모드 전환 실패
3. 알려진 주파수로 펄스를 인가하고 실측 fps가 그 값에 붙는지 확인
4. `CAP_PROP_BACKLIGHT = 0`으로 복귀

rack-tracker 실측에서 소프트 트리거로 이 관계가 이미 확인됐다(Hue=5 → 5.00fps,
Hue=30 → 15.00fps, 복귀 후 29.94fps). 같은 논리를 하드웨어 트리거에 적용한다.

통과하면 다이어그램의 FSIN 점선을 실선으로 바꾸고 `rig.json`에 마지막 검증 시각을
기록한다. 실패하면 점선 그대로 두고 실패 지점(2단계인지 3단계인지)을 표시한다 —
2단계 실패는 펌웨어/모드 문제, 3단계 실패는 배선/레벨 시프터 문제다.

**주의**: 설정을 전원 차단 후에도 유지하려면 설정 → 스트림 정상 종료 → USB 재삽입
순서여야 한다(벤더 문서 §3-7). 앱은 이 순서를 지키거나, 지키지 않는다면 설정이
휘발성임을 화면에 명시한다.

### 7.5 벤치마크

기존 `uvc_lab_presets.py`의 프리셋을 그대로 쓴다. 프리셋 하나 = 질문 하나라는 구조는
유지하고, 여기에 §8의 "어느 카메라를 어떤 상태로"라는 축이 붙는다.

### 7.6 로그

provision·기동·테스트 출력이 한 패널에 흐른다. 선행 문서에서 그대로 가져온다.

## 8. 테스트 프로필

"각 테스트마다 카메라 상태를 다르게"를 담는 그릇이다.

```jsonc
{
  "id": "sync-3cam-hw-trigger",
  "title": "하드웨어 트리거 3대 동기",
  "preset": "sync",
  "requires": {
    "controlProfile": "trigger-v1",
    "trigger": "fsin-hardware"
  },
  "cameras": {
    "usb-0:1.1": { "enabled": true, "mode": { "fourcc": "MJPG", "width": 1920, "height": 1200, "fps": 30 }, "trigger": "hardware" },
    "usb-0:1.2": { "enabled": true, "mode": { "fourcc": "MJPG", "width": 1920, "height": 1200, "fps": 30 }, "trigger": "hardware" },
    "usb-0:1.4": { "enabled": true, "mode": { "fourcc": "MJPG", "width": 1920, "height": 1200, "fps": 30 }, "trigger": "hardware" }
  }
}
```

`requires`가 이 명세의 핵심 장치다. 실행 버튼을 누르는 순간이 아니라 **프로필을
보여주는 순간** rig과 대조해서, 불가능한 조합이면 실행 버튼을 비활성화하고 이유를
적는다.

위 예시는 지금 장비에서 **실행 거부된다** — `usb-0:1.4`의 프로파일이 `webcam-std`라
`trigger: "hardware"`를 만족할 수 없다. 화면에는 이렇게 나온다.

> 실행할 수 없습니다 — 우측 카메라(P4)는 트리거 모드를 지원하지 않습니다
> (컨트롤 프로파일 `webcam-std`). 트리거 대상에서 빼거나 `trigger-v1` 카메라로
> 교체하세요.

실행 결과에는 프로필 id와 §5의 `rigStatus`를 같이 저장한다. **어떤 구성에서 나온
숫자인지 모르는 결과를 남기지 않는다.**

## 9. IPC 경계

renderer는 Node에 접근하지 않는다. preload `contextBridge`로 노출하는 것만 부른다.
장치·rig 관련 채널은 다음과 같다.

| 채널 | 방향 | 내용 |
| --- | --- | --- |
| `devices:list` | renderer → main | 현재 장치 열거 요청 (§2.2) |
| `devices:changed` | main → renderer | udev 변화 push (핫플러그) |
| `rig:get` | renderer → main | Jetson의 `rig.json` 읽기 |
| `rig:save` | renderer → main | 등록/수정 |
| `rig:match` | main → renderer | §5 대조 결과 (상태 + 포트별 상세) |
| `trigger:verify` | renderer → main | §7.4 검증 실행, 진행 상황 스트림 |
| `profile:run` | renderer → main | 테스트 프로필 실행 |
| `log:line` | main → renderer | 로그 한 줄 |

장치 열거와 rig 파일 입출력은 전부 Jetson에서 일어나므로, main은 SSH 또는 터널 위의
HTTP로 대행할 뿐이다. renderer는 어느 쪽인지 몰라도 된다.

## 10. Jetson 서버에 필요한 추가 엔드포인트

선행 문서는 `/api/health` 하나만 요구했다. 이 명세가 두 개를 더 요구한다.

| 엔드포인트 | 내용 |
| --- | --- |
| `GET /api/health` | 버전 + hostname (선행 문서) |
| `GET /api/devices` | **by-path 열거로 교체** (§2.2) + 컨트롤 프로파일 판정 (§2.4) |
| `GET /api/rig`, `PUT /api/rig` | `~/.uvc-lab/rig.json` 읽기·쓰기 |

`/api/devices`는 이미 있지만 index 스캔 기반이라 §1.4 때문에 교체 대상이다.

## 11. 구현 순서 개정

선행 문서의 9단계에 rig 관련 단계를 끼워 넣는다.

1. `serve_uvc_lab.py`에 `/api/health` 추가
2. **`uvc_devices.py` 열거 방식 교체** — index 스캔 → by-path (§2.2). 컨트롤 프로파일
   판정 포함 (§2.4). 이 장비에서 3대가 정확히 나오는지로 검증한다.
3. **`/api/rig` 읽기·쓰기** — 파일 하나 다루는 일이라 단독 검증 가능
4. `deploy/bootstrap.sh` + `deploy/uvc-lab.service`
5. `desktop/` 뼈대 — electron-vite + React + TS
6. main: 탐색(`discovery.ts`)
7. main: SSH + 프로비저닝(`ssh.ts`, `provision.ts`)
8. main: SSH 터널(`tunnel.ts`)
9. renderer: 장비 카드 + 로그 패널
10. **renderer: rig 등록 화면 + 배선 다이어그램** (§4, §6)
11. renderer: 랩 화면 — 프리뷰·모드·파라미터·벤치마크 (§7)
12. **renderer: 테스트 프로필 + `requires` 게이트** (§8)
13. 실제 Jetson으로 end-to-end 검증, 경로별 한 번씩 — **2026-08-19에 랜 직결
    경로로 수행했다.** 통과: 설치 9단계(aarch64, 실제 sudo/linger, uv 분기),
    SSH 터널 위의 HTTP, by-path 열거 3대(`trigger-v1`×2 + `webcam-std`), rig
    등록·저장, §5 대조 7종 중 `missing`/미등록 카메라 감지, 무시하고 진행 시
    `rigStatus` 기록, §7.2 모드 치환 표시, §7.3 컨트롤 읽기·쓰기, 벤치마크 실행,
    §8 게이트가 명세의 예시를 그 장비의 근거로 거부. 이 과정에서 앱 결함 7건을
    찾아 고쳤다(링크로컬 라우팅, link-local 전수 스캔, sudo exec 분리, 열거가
    프리뷰를 죽이는 문제, 재부팅 후 상태 불일치, 터널 미개방, 백그라운드에서
    실행 폴링 정지). USB/mDNS/Tailscale 경로는 미수행.

2번과 3번이 앞에 온 이유는 Electron 없이도 값이 나오고, §1.5 같은 문제를 제일 먼저
잡아주는 단계이기 때문이다.

## 12. 열린 항목

- **배선이 이 Jetson에 실제로 적용됐는지 확인되지 않았다.** GPIO 핀 기본값(BOARD 7 /
  BOARD 11)은 rack-tracker #161 설계에서 가져왔을 뿐 실물 확인이 아니다. 모든
  `wiring`은 `false`로 시작하고, §7.4를 통과하기 전까지 다이어그램에서 점선이다.
- **`STRB` 계측 경로는 명세에 없다.** rack-tracker의 STROBE 귀환은 로직 애널라이저를
  전제한 계측 계통이라 앱이 읽는 값이 아니다. `STRB` 체크박스는 "배선했다"는 기록일
  뿐이고, 앱이 그 신호로 무엇을 하는지는 정하지 않았다.
- **포트 4번 카메라를 어떻게 할지는 하드웨어 결정이다.** 트리거 3대 동기를 하려면
  `trigger-v1` 카메라로 교체해야 한다. 명세는 이 상황을 정확히 보고하는 것까지만
  책임진다.
- **허브 1번 포트가 불량이다(2026-08-19 확정).** 그 포트에 꽂힌 카메라는 열거에
  실패하고(`device not accepting address, error -71`) 재시도를 반복하다 Tegra의
  xHCI 컨트롤러를 죽였다(`HC died`) — 카메라 3대와 내장 블루투스가 한꺼번에
  떨어졌다. 같은 카메라를 같은 케이블로 3번 포트에 꽂으면 정상 동작한다. 포트를
  바꾸면 `camId`가 바뀌므로 rig도 다시 등록해야 한다(그 상황이 §5 대조를 실물로
  시험하는 조건이 됐다). 카메라 3대가 각각 512mA를 요구하므로 허브 전원도 함께
  의심할 대상이다.
- **mDNS 경로가 이 장비에서는 동작하지 않는다.** avahi가 서비스를 하나도 광고하지
  않아(`/etc/avahi/services/` 비어 있음, `publish-workstation=no`) `_ssh._tcp`
  조회로는 잡히지 않는다. `avahi-publish`가 설치돼 있으므로 사용자 단위 유닛으로
  광고를 띄우는 방법이 있고(sudo 불필요), 그 경우에도 첫 접속은 여전히 수동
  추가여야 한다. 아직 정하지 않았다.
- **컨트롤 프로파일 판별 조건이 2종뿐이다.** 다른 모듈이 들어오면 `unknown`으로
  떨어진다. 그때 조건을 추가하되, 판별 불가를 정상으로 위장하지 않는다.
